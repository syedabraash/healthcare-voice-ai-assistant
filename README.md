# Voice AI Patient Registration

A voice agent that answers a real phone number, conversationally registers a new
patient, persists the record, and exposes it through a REST API + small dashboard.

**Status: code complete, not yet deployed to a live number.** See
[Known Limitations](#known-limitations--trade-offs) — I built and unit-tested the
entire backend, the Vapi assistant config, and the tool-call webhook adapter, but
provisioning an actual phone number requires a Vapi/Twilio account (billing +
identity signup) that I don't have access to. Deployment steps below take about
15-20 minutes.

## Architecture

```
Caller ──dials──▶ Vapi (telephony + STT/TTS + LLM orchestration)
                        │
                        │ tool calls (lookupPatientByPhone / createPatient / updatePatient)
                        ▼
              POST /vapi/webhook  ──┐
                                     │  app/vapi_webhook.py (adapter layer)
                                     ▼
                              app/crud.py (service layer)
                                     │
                                     ▼
                          SQLite database (app/models.py)
                                     ▲
                                     │
                    GET/POST/PUT/DELETE /patients  ◀── REST clients / dashboard
                              (app/main.py)
```

**Separation of concerns**, deliberately:
- `app/main.py` — the public REST API. Knows nothing about Vapi.
- `app/vapi_webhook.py` — translates Vapi's tool-call envelope into calls against
  the same service layer the REST API uses. If you swapped Vapi for Retell or a
  raw Twilio+GPT stack tomorrow, only this file would change.
- `app/crud.py` — the actual data operations, shared by both entry points.
- `app/schemas.py` — all validation lives here (Pydantic), enforced server-side
  regardless of what the voice agent thinks is valid.
- `vapi/system_prompt.md` + `vapi/assistant_config.json` — the conversational
  design, documented separately from the JSON that carries it.

## Tech stack & why

| Layer | Choice | Why |
|---|---|---|
| Voice/telephony | **Vapi** | Abstracts STT/TTS/telephony so the 3-hour budget goes into prompt design and tool integration, not audio plumbing. Native Claude support as the model provider. |
| Backend | **FastAPI (Python)** | Async-friendly, built-in request validation + OpenAPI docs, minimal boilerplate for a CRUD API under time pressure. |
| Database | **SQLite via SQLAlchemy** | Zero-ops persistence — a file on disk, no separate DB server to provision or keep alive on a small deploy. Swapping to Postgres later is a one-line `DATABASE_URL` change since the code uses the SQLAlchemy ORM, not raw SQLite calls. |
| Hosting | **Railway or Render** (see below) | Both support "push a repo, get an HTTPS URL" in a few minutes, which is what actually matters for the live-review requirement. |

## Data model

All fields from the spec are implemented in `app/models.py` with matching
constraints in `app/schemas.py` (name character rules, US phone normalization to
10 digits, ZIP / ZIP+4 format, valid 2-letter state codes, DOB not in the future,
enum-checked `sex`). `patient_id` is a UUID primary key; `created_at`/`updated_at`
are UTC timestamps; deletes are soft (`deleted_at`), never destructive.

## REST API

All responses use the envelope `{ "data": ..., "error": null }`.

| Method | Endpoint | Notes |
|---|---|---|
| GET | `/patients` | Optional `?last_name=`, `?date_of_birth=`, `?phone_number=` |
| GET | `/patients/{id}` | 404 if missing or soft-deleted |
| POST | `/patients` | 201 on success, 422 with field errors on invalid input |
| PUT | `/patients/{id}` | Partial update — only send fields you're changing |
| DELETE | `/patients/{id}` | Soft delete (`deleted_at` set, row kept) |
| GET | `/health` | Liveness check |
| GET | `/` | Dashboard UI (bonus) |

Interactive docs are auto-generated by FastAPI at `/docs` once running.

## Voice agent design

The full system prompt and reasoning behind its structure live in
[`vapi/system_prompt.md`](vapi/system_prompt.md) — read that file, it's short and
explains *why* each behavior (confirmation loop, correction handling, restart
handling, optional-field opt-in) is written the way it is, not just what it says.

Three tools connect the LLM to the backend (defined in
`vapi/assistant_config.json`, handled in `app/vapi_webhook.py`):
- `lookupPatientByPhone` — duplicate-caller detection (bonus requirement)
- `createPatient`
- `updatePatient`

## Local setup

```bash
git clone <this-repo>
cd voice-ai-patient-registration
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt
cp .env.example .env          # defaults work as-is for local dev
python seed.py                # optional: inserts 2 demo patients
uvicorn app.main:app --reload --port 8000
```

Visit `http://localhost:8000` for the dashboard, `http://localhost:8000/docs` for
the API explorer.

Run tests:
```bash
pytest tests/ -v
```
(9 tests covering creation, validation failures, filtering, partial update,
soft-delete visibility, and a persistence check that mirrors the "call back and
the data should still be there" requirement.)

## Deploying to get a live number (what's left to do)

**1. Deploy the backend** (Render used as the example):
- Push this repo to GitHub.
- Render → New → Web Service → connect the repo.
- Build command: `pip install -r requirements.txt`
- Start command: `uvicorn app.main:app --host 0.0.0.0 --port $PORT`
- Add env vars from `.env.example` (`DATABASE_URL=sqlite:///./patients.db` is fine
  for a single instance; `VAPI_WEBHOOK_SECRET` = any random string you generate).
- **Caveat:** most free tiers use ephemeral disks, so a redeploy can wipe the
  SQLite file. For the review call, that's fine (fresh reviewer data is
  expected); for real persistence guarantees, attach a persistent volume (Render
  supports this on paid plans) or point `DATABASE_URL` at a managed Postgres
  instance — no code changes needed either way.
- Note the resulting URL, e.g. `https://your-app.onrender.com`.

**2. Create the Vapi assistant:**
- Sign up at vapi.ai, add an Anthropic (or OpenAI) API key under Provider Keys.
- Open `vapi/assistant_config.json`, replace both `<PUBLIC_BASE_URL>` placeholders
  with your deployed URL from step 1, and `<VAPI_WEBHOOK_SECRET>` with the same
  string you set in the backend's env vars.
- Paste the prompt block from `vapi/system_prompt.md` into the `model.messages[0].content`
  field (the JSON currently just points at that file).
- Import via the API:
  ```bash
  curl -X POST https://api.vapi.ai/assistant \
    -H "Authorization: Bearer $VAPI_API_KEY" \
    -H "Content-Type: application/json" \
    -d @vapi/assistant_config.json
  ```
  (or paste the fields into the dashboard's assistant builder by hand.)

**3. Buy/assign a phone number:**
- Vapi dashboard → Phone Numbers → Buy a number (or import an existing Twilio
  number) → attach it to the assistant created above.
- That number is what you send to the reviewer.

**4. Smoke test before submitting:** call the number yourself, register a test
patient, hang up, then `GET /patients` (or check the dashboard) to confirm the
record is there — and call again to confirm a second run doesn't wipe the first.

## Known limitations & trade-offs

- **Not deployed by me.** I don't have a Vapi/Twilio/hosting account to
  provision a real phone number or push a live deploy from this environment —
  the steps above are what's needed and are accurate to Vapi's current API, but
  untested against a live account. Budget ~15-20 minutes to complete them.
- **SQLite, not Postgres.** Right choice for a 3-hour scope per the assessment's
  own guidance; noted as a trade-off, not an oversight. Swapping is a
  `DATABASE_URL` change only.
- **Webhook auth is a shared-secret header**, not Vapi's newer HMAC/timestamp
  signing option. Adequate for an assessment; for production I'd switch to a
  Custom Credential with HMAC verification (Vapi supports this directly).
- **No call-transcript persistence to the DB** — transcripts are logged to
  stdout on `end-of-call-report` (satisfies the observability requirement) but
  not linked to the patient row in the schema. Listed here rather than silently
  skipped since it's one of the bonus items.
- **No automatic retry/backoff on DB write failure** inside the webhook handler
  — a failed write returns a clear error to the agent (which relays it to the
  caller per the prompt design) rather than silently succeeding, but doesn't
  retry automatically.
- **Multi-language support is prompt-level only** (the agent is instructed to
  switch to Spanish on request) — there's no separate localized prompt/voice
  configuration, so quality depends on the underlying model's Spanish fluency
  rather than a tuned Spanish-specific flow.
